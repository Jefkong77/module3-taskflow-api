# TaskFlow exploratory data and requirements analysis

Prepared for Ms. Sanjela • Jeffrey Kong • 23 October 2026

## Purpose and scope

TaskFlow is a small task management backend for recording actions and tracking whether each action is complete. The assessed deliverable is a Java 21 Spring Boot API with four layers, an in-memory collection, six endpoints, and a public GitHub repository URL submitted through NTU Learn.

This analysis explains the problem, data contract, design choices, and verification approach before implementation. No operational dataset was supplied. The accompanying six records are synthetic examples for exploring the schema; they are not observations about real users or evidence of market demand. EDA is supporting documentation, not an additional assignment requirement.

## Context and intended user

A learner or project coordinator needs to add an action, list actions, retrieve one action, update it, mark it complete, and delete it. For example, a research action could later support a market research workflow. This submission remains a task API with the required task resource and fields.

The API is exercised through Postman. A dashboard, React interface, database, authentication, RAG, MCP, and deployment are outside this mandatory assignment. PostgreSQL, DBeaver, JPA, and SQL are not used because the brief explicitly requires an ArrayList or HashMap in memory.

## Data dictionary

| Field | Java type | JSON type | Meaning and ownership |
| --- | --- | --- | --- |
| id | Long | number | Unique identifier generated by the repository counter. Client IDs do not determine creation IDs. |
| title | String | string | Description of the action. The service trims it and accepts 1–200 characters after trimming. |
| completed | boolean | boolean | false means pending; true means complete. Omission defaults to false. |

The three fields are required by the brief. The 200-character limit and title trimming are implementation decisions, not assessment requirements. A Jackson setting explicitly makes omitted or null completed values false, preserving the primitive boolean default with this generated Spring Boot version. PUT replaces title and completed together; clients should send both writable fields. The path ID identifies the record being updated, even if the body contains another ID.

## Synthetic data exploration

The sample in `sample-tasks.csv` contains six illustrative records. IDs are unique, titles are populated, and completed values are boolean categories. Three records are complete and three are pending, giving an illustrative completion proportion of 3 / 6 = 50%. This value describes the fixture only; it is not an application usage statistic.

The sample intentionally contains both completion states. It is not automatically loaded: a fresh application starts with an empty collection. Validation and missing-resource cases are tested separately; invalid rows are not mixed into the valid fixture.

## Lifecycle and API contract

Create produces a new server ID and accepts an initial completion state. Normal examples start pending. The dedicated complete operation sets completed to true and saves the task back; repeating it leaves the task complete. PUT can deliberately change completed back to false. DELETE removes the record.

| Operation | Method and path | Successful status |
| --- | --- | --- |
| List | GET /api/tasks | 200 |
| Read | GET /api/tasks/{id} | 200 |
| Create | POST /api/tasks | 201 |
| Update | PUT /api/tasks/{id} | 200 |
| Delete | DELETE /api/tasks/{id} | 200 |
| Complete | PUT /api/tasks/{id}/complete | 200 |

The specified success codes apply to valid operations. Unknown positive IDs return 404. Invalid IDs, missing or blank titles, overlong titles, and malformed JSON return 400. These error behaviours are additional design choices that make failures explicit.

## Architecture and rationale

The controller translates HTTP requests and responses and calls the service through constructor injection. The service validates input and implements the six required operations. The repository owns the initialized HashMap, ID counter, and storage operations. Task is a plain POJO using Lombok getters, setters, and constructors; it has no Spring or JPA annotations.

A HashMap supports direct lookup by ID. Repository methods are synchronized to protect individual map operations and ID allocation. Returned objects are copies, so changing a response object in Java does not silently change storage. Lists are sorted by ID for predictable demonstrations. Multi-step service operations are not a transactional or multi-instance persistence design.

## Limitations and possible continuation

Restarting the process or triggering a DevTools restart clears tasks and resets IDs. There is no database, user ownership, or authentication. These limits match the exercise scope. Optional Task 6 is not implemented in this baseline; no AI key is needed.

A later learning project could replace storage with PostgreSQL and add a React task screen. Such work should follow the assessed submission. Opportunity records and Task records have different schemas and resource paths, so a TaskFlow URL cannot directly replace the India Opportunity Navigator opportunity API.
