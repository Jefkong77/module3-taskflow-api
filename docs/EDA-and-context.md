# TaskFlow exploratory data and requirements analysis

## Problem and use case

TaskFlow records project actions and tracks whether each action is complete. A user can create a task, list tasks, retrieve one task, update its details, mark it complete, or delete it. The Spring AI summary provides a short account of pending and completed work.

The Module 3 assignment specifies a Java 21 Spring Boot backend with model, repository, service, and controller layers. The repository stores tasks in memory using a collection. Postman provides the interface for exercising the API.

## Data dictionary

| Field | Java type | JSON type | Meaning |
| --- | --- | --- | --- |
| id | Long | number | Identifier generated by the repository counter |
| title | String | string | Description of an action; trimmed to 1–200 characters |
| completed | boolean | boolean | false for pending; true for complete |

The three fields form the assignment's minimum task model. Title trimming and the 200-character maximum are implementation choices. Creation ignores a client-supplied ID. During an update, the URL ID identifies the stored record. PUT replaces title and completed together. Omitted or null completed values bind to false.

## Sample data

[Sample tasks](sample-tasks.csv) contains six synthetic project-planning records. The examples cover meeting preparation, scheduling, and budget review. They illustrate the schema and completion states; the application starts with an empty task collection and does not import this file.

| Measure | Sample result | Interpretation |
| --- | --- | --- |
| Records | 6 | Six example actions |
| Unique IDs | 6 | Each example has a distinct identifier |
| Missing titles | 0 | Every action has a description |
| Completed tasks | 3 | Examples with completed = true |
| Pending tasks | 3 | Examples with completed = false |
| Completion proportion | 50% | 3 completed records divided by 6 sample records |

The completion proportion describes this synthetic sample. It is a schema and lifecycle example, rather than a usage metric.

## Task lifecycle

Creation allocates an ID and stores the supplied title and completion state. The dedicated completion operation sets completed to true and saves the task; repeating it keeps the task complete. PUT can update the title or set completed back to false. DELETE removes the record.

| Operation | Endpoint | Result |
| --- | --- | --- |
| Create | POST /api/tasks | 201 and the saved task |
| List | GET /api/tasks | 200 and a task array |
| Retrieve | GET /api/tasks/{id} | 200 and one task |
| Update | PUT /api/tasks/{id} | 200 and the updated task |
| Complete | PUT /api/tasks/{id}/complete | 200 and completed = true |
| Delete | DELETE /api/tasks/{id} | 200 and a confirmation |
| Summarise | GET /api/tasks/summary | 200 and plain-English text |

Invalid IDs, blank or missing titles, overlong titles, and malformed JSON return 400. Unknown positive IDs return 404. These responses make invalid operations explicit.

## Design implications

A HashMap provides lookup by ID and satisfies the collection-based storage requirement. A counter generates IDs. Repository methods return copies and sort lists by ID for predictable responses. Synchronized methods protect individual storage operations and counter increments.

Tasks last for the application session. A process or DevTools restart starts an empty collection and resets IDs. This storage behaviour is part of the exercise design.

The summary uses stored titles and completion states. Its prompt includes completed and pending counts, treats titles as data, and requests at most three short sentences. Stored task records remain the reference when interpreting the generated text.
